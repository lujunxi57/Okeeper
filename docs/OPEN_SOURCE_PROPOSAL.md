# Okeeper 开源产品化方案

日期：2026-10-22。状态：产品与实施建议，附交互原型；跨平台版本和云端版本尚未实现或验收。

## 1. 建议先确定的方向

**Okeeper：Codex 的定时与额度助手。**

主文案：**按时发消息，随时看额度。**

面向已经在使用、或愿意开始使用 Codex 的个人用户。首个公开版本要让用户无需 Linux 服务器、无需安装 Python、无需编辑配置文件，就能完成一次定时消息。开源软件免费不代表模型调用、账号订阅或云资源免费。

采用一个项目、同一套执行核心，提供两种使用方式：

| 使用方式 | 用户需要准备什么 | 电脑睡眠或关机后 | 适合谁 |
| --- | --- | --- | --- |
| 本地版，默认入口 | 自己的电脑、可用的 Codex 账号 | 无法保证按时执行；恢复后按设置补发或跳过 | 大多数日常桌面使用者 |
| 自托管版，进阶入口 | 一台支持版本的常开设备、独立登录 | 只要远端在线，任务仍在远端执行 | 已有服务器、NAS 或其他常开设备的人 |
| 后续云部署模板 | 云平台账号和资源费用 | 由选定云平台上的常驻服务执行 | 没有设备，但愿意承担云资源费的人 |
| 未来托管服务 | 服务账号及可能的订阅费用 | 由运营方承担持续运行 | 不愿部署和运维的人 |

后两项属于后续产品选择。首版不展示“免费云端”“托管已开放”之类入口。

**Linux 是安装障碍；持续执行需要常开算力。** 把程序搬到普通电脑上可以解决第一件事。要在电脑关闭时继续执行，仍然要有另一台运行任务的机器。云端仅发送一个唤醒信号，不能让已经睡眠的本地进程自行工作。

## 2. 从现有项目出发

本轮阅读了当前工作区源码和项目文档，未执行真实账号推理、切号、部署或跨平台安装。

| 已有基础 | 对开源版本的价值 | 需要处理的限制 |
| --- | --- | --- |
| HTML/CSS/JS、Python、SQLite | 继续复用界面、任务存储和执行记录 | 增加跨平台启动和打包 |
| 按账号定时触发、手动试运行 | 首版核心功能已有业务基础 | 固定模型、固定时区需要移除 |
| 额度查询、请求历史 | 可以形成简洁的日常工作台 | 区分过期数据、未提交、已提交和完成 |
| 独立 app-server 的 stdio 实现 | 为跨平台执行提供起点 | 当前外部凭据注入方式不适合作为普通用户默认登录入口 |
| 指定会话发送、切号、continue | 保留进阶用户的项目特色 | 依赖具体后台，不能宣称各种桌面/CLI/IDE 都能接管 |
| systemd 安装和调度 | 已有 Linux 部署可继续维护 | 当前不是通用桌面程序 |

具体源码位置：

- `scripts/install_services.py`：用户级 systemd 服务安装。
- `app/account_dispatch.py:13`：每次任务通过 `systemd-run` 启动。
- `app/rpc.py:3`：主后台连接使用 Unix socket。
- `app/trigger.py`、`app/account_control.py`：使用 `fcntl`；前者固定 `Asia/Taipei`。
- `app/settings.py`：Linux 风格的默认状态目录与后台地址。
- `app/account_rpc.py:31`：独立 `app-server`、stdio 通信及现有凭据注入。
- `app/web_server.py:38`、`:82`：有同源限制，但没有远程用户身份认证；当前 API 不适合直接暴露到公网。

当前根目录未见项目级 LICENSE。README 写明需要 Linux、systemd 和已运行的 Codex 后台。因此本次目标不能仅靠更换 README 或添加 Dockerfile 完成。

## 3. 普通用户应该怎样使用

### 安装与首次打开

正式发布目标是 Windows/macOS 可安装程序；Linux 保留已有使用路径，再提供经验证的桌面包或自托管镜像。每个系统、CPU 架构和 Codex 版本分别标注支持状态，未测试的不写“支持”。

默认进入本地设置，不先问用户选本地还是云端。

1. **连接账号。** 检测 Codex 组件及兼容性。缺少组件时提供带来源、版本和进度的安装引导；已有组件则使用经过验证的版本。通过官方浏览器授权或设备码登录，避免让用户寻找、复制 `auth.json`。用户选择账号后，展示实际身份。
2. **设置时间。** 选择每天或仅一次、时间和轻量消息使用的模型。初始采用系统时区，并把时区保存到任务；出差或更改系统时区时，询问是否修改安排，避免任务时间悄悄改变。轻量任务提供“错过后 2 小时内补发最近一次”的明确选择。
3. **试运行并开启。** 先说明会使用一次模型调用；得到真实完成回执后，才确认该账号与模型能执行，并让用户开启安排。模型列表只是目录，不是可用性证明。后续模型不可用时提示用户选择和测试其他模型，不自动替换。

组件是否能直接随安装包分发、设备码登录在目标账号上的可用性，都要在可行性阶段核验。安装引导失败时给出具体处理办法，不把“请配置 Python、Node、PATH、systemd”作为正常用户路径。

### 工作台

首页只保留下一次安排、账号额度、定时列表和最近结果入口。完整历史在“运行记录”，设备连接在“运行位置”。单账号时不出现主账号、路由、Home 等概念。

用户需要随时知道三件事：**什么时候发、在哪台设备发、这一次有没有完成。**

- 窗口关闭后是否继续运行，在托盘设置里说清楚；“关闭窗口”和“退出 Okeeper”分开。
- 登录系统后自动启动由用户选择。托盘常驻不等于可以绕过系统睡眠。
- 额度显示数据更新时间；读取失败时保留旧值及过期标识，不能显示成实时正常。
- 多账号加入后才显示账号选择。自动切号、切号后继续和指定已有会话定时提示放到进阶设置；自动切号默认关闭，并说明它可能中断正在执行的任务。
- 首版只对 Okeeper 自己管理的轻量会话作跨平台承诺。连接既有 Codex 会话按具体运行环境单独验收。

### 睡眠和错过时间

| 情况 | 行为 | 用户看到什么 |
| --- | --- | --- |
| 到点、设备和登录正常 | 领取任务并投递 | 执行中 → 已完成，或明确错误 |
| 设备恢复，轻量任务确认未提交，开启补发且仍在 2 小时内 | 只补最近一次 | 已补发，并标原定时间和实际时间 |
| 超过补发时限，或未开启补发 | 跳过当次 | 已错过，附可核实的原因 |
| 已提交，完成结果不确定 | 查询原请求，不重复投递 | 结果待确认 |
| 登录失效或模型不可用 | 暂停该任务的投递，保留安排 | 需要登录 / 更换模型 |

“确认未提交”和“提交后没有拿到回执”必须区分。若没有取得 turn ID 且无法核查，保留待确认状态，不能自动当作失败重新发送。

如果系统仅知道进程未运行，不应把原因写死为“电脑睡眠”。用户界面可以显示“设备离线，未执行”；确有电源事件记录时再显示睡眠原因。

指定会话的自定义消息默认错过即跳过，避免醒来后向工作会话补发过时指令。插电时阻止空闲睡眠可后续提供，必须由用户启用并在真实系统验证；不保证合盖唤醒，也不静默改变系统电源设置。

## 4. 云端版的实际范围

### 首个远程版本：单用户自托管

发布同一执行核心的容器镜像、持久卷配置、更新说明，以及手机也能使用的管理页面。先验证 Linux x86_64；ARM/NAS 机型通过安装与执行验收后再加入支持矩阵。

用户在常开设备上部署并登录，在桌面或手机中连接。界面采用一次性配对链接/配对码，把连接凭据导入客户端，不要求日常用户手敲长 Token。配对后凭据可撤销，配对码短期有效且限制尝试次数。第一版只管理单用户设备，不先增加组织、团队、角色和共享账号。

私网部署是默认文档路径；需要公网访问时使用 TLS 和身份认证。不要把当前本机 API 改成 `0.0.0.0` 就称为云端版。管理接口与 Codex 内部连接分离，不能公开原生 app-server 控制端口。

远端独立保存任务、执行记录和登录。连接界面只切换当前管理位置，不自动同步两个数据库，不自动搬移会话，也不在失败时跨设备重发。用户修改云端任务时，应当清楚看到“运行在我的云端”。

**云端可以执行它自己的任务；不能接管只存在于睡眠电脑里的会话、未上传文件和本地工作目录。** 未来若支持迁移，要单独处理账号、项目和会话兼容，不能仅复制一个会话 ID。

### 没有服务器的人

要进一步降低门槛，下一步选择一家支持常驻进程、持久磁盘和当前登录方式的云平台，制作经过实际部署验证的模板。发布时提供当时的资源费用说明、数据位置、升级方式和删除方法，不预先承诺免费或精确价格。

真正“注册即用”的托管服务，意味着运营方要承担资源成本、账号隔离、服务可用性、升级和支持工作。这是后续独立产品决策，不是给开源仓库加一个开关。没有运营安排前，文档说明路线即可，产品中不放无法兑现的按钮。

不将 GitHub Actions 定时工作流作为默认云端。GitHub 官方明确说明定时可能延迟，负载过高时可能丢弃任务；临时执行环境也不自然拥有本地会话和长期登录状态。技术用户的宽松时间任务可以另行探索，不能用于承诺准点与持久会话。[GitHub 官方说明](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows#scheduled-workflows-running-at-unexpected-times)

## 5. 工程方案：复用核心，逐步解除绑定

```text
本地：桌面窗口 / 托盘 → Okeeper runner → Codex app-server（stdio）
                              ↓
                       本机 SQLite + 原生登录存储

远程：手机网页 / 桌面连接 → 认证后的管理接口 → 同一个 Okeeper runner
                                                   ↓
                                         远端 SQLite + 原生登录存储
```

### 先改什么

1. 把到期检查和执行启动收进一个常驻进程。systemd 留作 Linux 上的启动方式，移除每个任务必须依赖 `systemd-run` 的假设。
2. 默认由 Okeeper 管理自己的 app-server，通过 stdio 通信；现有 Unix socket 作为支持环境中的进阶连接方式。官方文档提供 stdio、登录流程、额度读取及任务事件，可作为兼容实现依据，仍需对选定版本实际验证。[Codex App Server](https://learn.chatgpt.com/docs/app-server)
3. 将 `fcntl`、路径、进程退出、时区及后台启动封装为少量明确的平台差异，不为尚不存在的平台设计插件系统。SQLite 原子领取与单实例运行解决实际重复调度问题。
4. 保留现有任务、执行结果和账号隔离逻辑，增加任务时区及运行位置的明确展示，移除固定模型。使用安装包锁定并验收的 Codex 版本，升级时检查协议兼容。
5. 桌面壳先做 Tauri + 打包后的 Python 执行器试验。Tauri 官方支持外部二进制 sidecar，也举出了 Python/PyInstaller 的用法；这只证明组合方式受支持，不证明 Okeeper 已能跨平台安装。[Tauri sidecar 文档](https://v2.tauri.app/develop/sidecar/)

内部开发预览可以单命令启动本地 Web 界面；普通用户正式版本仍以可安装程序验收。若打包试验不合适，根据试验结果选择另一种壳，不并行维护 Tauri 和 Electron 两套实现。

### 只保留有实际用途的保护

任务领取前持久化，键包含任务 ID、版本和计划时刻；重启不重复领取同一次任务。提交前再次核对任务是否取消、账号和位置是否仍匹配。已取得 turn ID 后持续核验同一个请求；通信结果不明时不自动重发。不能宣称“绝对恰好执行一次”。

登录由 Codex 的受支持原生流程完成；Okeeper 使用独立状态位置，避免为了定时消息改写用户正在使用的主账号。实际凭据存储方式跟随所验证的 Codex 平台实现。远端凭据留在执行端，页面与诊断导出不返回原始登录文件。

任务继承或使用事先声明的权限，不自动批准工具请求。第一版轻量消息不需要开放项目写入。需要用户处理的任务明确停止等待，不能用“自动化”替代授权。

不引入 Redis、Kubernetes、分布式任务队列、自动跨设备接管、通用 provider 插件体系或无限重试。先把一个人、一台执行设备、一个任务的结果做清楚。

### 运行记录与存储

保留三个概念即可：安排、一次执行、本机设置。账号与会话身份引用现有记录。记录原定时间、实际提交时间、实际运行位置、账号、模型、请求标识、完成状态和必要错误。历史中缺失的字段显示“未记录”，不能用当前账号反推历史。

每天任务按保存的 IANA 时区计算。夏令时重复时刻只执行一次；不存在的时刻按明确策略跳过并记录。修改任务时间后更新任务版本，取消旧待执行项。不要通过“每隔 24 小时”替代用户选择的当地钟点。

## 6. 版本顺序和验收

以下是建议的交付次序，不是已经完成的功能，也不承诺未经估算的工期。

| 阶段 | 交付 | 通过条件 |
| --- | --- | --- |
| 可行性样机 | Windows/macOS 上的 runner、登录和 stdio；Linux 容器试验 | 两种桌面系统分别完成真实登录、定时投递、完成回执和退出清理；确认安装包可行。桌面既有会话连接另测 |
| 公开桌面预览 | 可安装程序、基础引导、单账号额度、单次/每日消息、模型确认、历史、托盘/自启动 | 干净机器无需 Python 和终端完成第一条消息；关窗口、退出、重启、睡眠恢复行为符合界面说明 |
| 自托管发布 | 同一核心的镜像、配对、手机页面、持久卷与升级流程 | 本地电脑关闭后，远端任务完成且有真实回执；远端重启保留任务、登录和历史，未重复执行 |
| 扩展阶段 | 云部署模板；进阶多账号、既有会话适配；托管可行性评估 | 每项单独提供现场证据和支持范围，再公开标记可用 |

大众桌面版首发范围最多八项：安装包、环境与登录引导、额度概览、一次/每日轻量定时、明确模型和试运行、错过处理、执行记录、托盘与自启动。已有高级功能保留在现有 Linux 维护路径中，不为简化新界面删除用户已有能力和数据。

拟定用户验收：邀请 5 位没有参与开发的 Codex 用户，至少 4 位在 10 分钟内不借助终端完成首次成功试运行，并能正确回答“睡眠时是否执行”和“任务在哪里运行”。这是待验证目标，不是当前统计结果。

工程验收需覆盖：一次真实完成、提交后断线、进程重启、睡眠恢复、时区变化、重复点击、登录失效、模型不可用、升级与恢复。浏览器模拟和健康检查只能证明相应界面/服务行为，不能替代真实调用和原机安装验收。

## 7. 开源发布需要补齐什么

- **仓库边界：** 发布明确的源码集合，检查源码和 Git 历史中的凭据、账号数据、个人路径、数据库和生成产物。不要从自用目录直接压缩上传。若历史中发现敏感信息，先处理凭据和发布边界，再决定是否重写公共历史。
- **许可证：** 确定项目级开源许可证。建议将 Apache-2.0 作为候选，发布前确认作者权利和依赖许可，补充 LICENSE，保留已有第三方声明；本轮不替维护者作最终许可决定。
- **下载入口：** 首页显著区分“下载桌面版”“自己部署”“参与开发”。给出各系统已验证安装包、校验信息、签名/公证状态及版本，避免把源码 ZIP 当作普通用户安装包。
- **文档：** 中英文 README、三步入门、运行位置说明、睡眠与额度 FAQ、支持矩阵、升级/卸载、备份恢复、贡献指南、脱敏问题模板和版本日志。
- **用户支持：** 应用内提供“复制诊断信息”，只包含版本、系统、运行状态与可公开错误；导出前预览，不夹带登录文件、提示词全文和个人路径。
- **构建与升级：** 各平台自动构建，记录 Codex 兼容版本。首次采用可检查、可回退的更新流程；数据迁移前备份，测试从已有版本升级，而不只测试全新安装。

默认不增加后台使用追踪。先通过志愿试用、问题反馈和可选择的诊断信息发现卡点。是否开放托管、如何承担签名和云资源费用，在取得实际需求后决定。

## 8. 原型说明

原型展示：本地工作台、首次设置三步、添加/编辑/暂停时间、模拟执行及回执、本地睡眠后的补发、登录失效、结果待确认、连接虚构云端设备及独立记录。可切换演示场景查看差异。

原型仅使用示例账号和模拟结果，未接真实服务。它固定演示日期、时区和轻量消息，未实现系统安装、真实授权、真实模型选择、通知、单次日期或实际后台定时器。这些仍在正式实施范围内。

手机布局只表示手机可以管理；不表示手机浏览器能在后台持续运行 Codex。
